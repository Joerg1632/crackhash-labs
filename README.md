# CrackHash — Лабораторная работа №2: Отказоустойчивость

## Что добавлено по сравнению с лабораторной №1

- **MongoDB Replica Set** — хранение состояния запросов (1 primary + 2 secondary)
- **RabbitMQ** — надёжная доставка задач и результатов между компонентами
- **Отказоустойчивость** менеджера, воркеров и очереди

---

## Очереди RabbitMQ

Две независимые очереди с direct exchange:

| Очередь   | Направление       | Назначение                      |
|-----------|-------------------|---------------------------------|
| `tasks`   | Manager → Workers | Отправка диапазонов для перебора |
| `results` | Workers → Manager | Возврат найденных слов          |

Все сообщения **персистентны**. Воркеры используют **manual acknowledgement** —
при падении воркера задача автоматически возвращается в очередь и забирается другим.

---

## MongoDB Replica Set

Схема: **1 primary + 2 secondary**.

Менеджер подтверждает принятие запроса клиенту только после записи
с write concern `majority` — то есть после репликации на большинство нод.
При падении primary нода переизбирается автоматически.

---

## Сценарии отказов

| Сценарий | Поведение |
|---|---|
| Падение менеджера | Запросы сохранены в MongoDB; ответы воркеров ждут в очереди `results` до рестарта |
| Падение воркера | Задача возвращается в очередь и забирается другим воркером |
| Падение RabbitMQ | Менеджер сохраняет неотправленные задачи в MongoDB и повторяет отправку после восстановления |
| Падение primary MongoDB | Replica Set переизбирает primary, система продолжает работу |
| Дублирование задач | Повторно полученные результаты по завершённой задаче игнорируются менеджером |
