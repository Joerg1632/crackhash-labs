# CrackHash — Лабораторная работа №2: Отказоустойчивость

## Что добавлено по сравнению с лабораторной №1

- **MongoDB Replica Set** — хранение состояния запросов (1 primary + 2 secondary)
- **RabbitMQ** — надёжная доставка задач и результатов между компонентами
- **Отказоустойчивость** менеджера, воркеров и очереди

---

## Очереди RabbitMQ

Две независимые очереди с direct exchange:

| Очередь   | Направление       | Назначение                       |
|-----------|-------------------|----------------------------------|
| `tasks`   | Manager → Workers | Отправка диапазонов для перебора |
| `results` | Workers → Manager | Возврат найденных слов           |

Все сообщения **персистентны** — записываются на диск и переживают рестарт RabbitMQ.
Воркеры используют **manual acknowledgement** — при падении воркера задача
автоматически возвращается в очередь и забирается другим.

---

## MongoDB Replica Set

Схема: **1 primary + 2 secondary**.

При падении primary оставшиеся ноды выбирают нового — для этого нужно большинство
голосов (2 из 3). При падении двух нод система переходит в read-only до восстановления.

Менеджер при старте подхватывает незавершённые запросы из MongoDB и переотправляет
их задачи в RabbitMQ.

---

## Сценарии отказов

| Сценарий | Поведение |
|---|---|
| Падение менеджера | Запросы сохранены в MongoDB; ответы воркеров ждут в `results` queue; при рестарте менеджер переотправляет незавершённые задачи и подбирает накопившиеся результаты |
| Падение воркера | Unacked задача возвращается в очередь и забирается другим воркером |
| Падение RabbitMQ | Персистентные сообщения восстанавливаются с диска после рестарта |
| Падение primary MongoDB | Replica Set автоматически переизбирает primary из оставшихся нод |
| Дублирование задач | Возможно при рестарте RabbitMQ — повторные результаты дедуплицируются менеджером |
